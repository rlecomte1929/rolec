# ReloPass Platform UI Audit

Date: 2026-06-13

Scope: production public site, HR portal, employee portal, admin console, targeted API validation, and local UI fixes.

Evidence: `.context/ui-audit-2026-06-13/screenshots/` (34 production screenshots plus 2 local verification attempts).

## Executive Summary

- Public positioning is structurally strong below the fold, but the production hero currently leads with AI compliance rather than the operating-layer category. This was fixed locally.
- The HR case detail masks a `500` from `GET /api/cases/{id}/vendors` and the automated suite finds `GET /api/hr/cases/{id}` returning `404`.
- Employee services persistence is broken: both read and write calls to `/api/cases/{assignmentId}/services-state` return `403` while the UI continues as if state were saved.
- Core authenticated pages are slow. Observed production requests took 3.5-7.7 seconds, including the HR assignment list and employee assignment overview.
- The policy workspace rendered a live Matrix v4 and a no-policy onboarding state at the same time. The local resolver now treats the normalized published version as authoritative.
- The targeted API run scored 81%: 39 pass, 7 fail, 2 warn, 1 skip. Fresh-registration failures were rate-limit contamination and are not counted as product findings.

## Phase 2: Design Critique

### 2-A HR Case Creation

Overall: The requested multi-step wizard does not exist in the tested production path. Clicking New case reveals First name, Last name, Employee username or email, Seniority level, and Assign inline above the case table.

| Area | Finding |
|---|---|
| First impression | "New case" does not explain that this creates a draft case before assignment. |
| Usability | A POST to `/api/hr/cases` occurs when opening the form; Assign then calls `/api/hr/cases/{id}/assign`. Abandoning the form can leave drafts. |
| Hierarchy | The form competes visually with filters and the full case table. |
| Consistency | There is no staged validation for route, dates, household, policy, or owner. |
| Accessibility | Inputs are labelled and keyboard reachable; primary flow is compact but lacks step context. |

Top changes: create the case only after explicit confirmation, stage required relocation fields, and land on the newly created case detail instead of remaining on the table.

### 2-B Employee Onboarding and Task Completion

Overall: The high-level journey is understandable, but the demo state is overloaded and persistence failures undermine trust.

- The first useful content arrives after a 7.7-second assignment request.
- "What you can do now" correctly prioritizes one action, but Tasks says no work is assigned while Roadmap shows overdue work.
- Services displays choices despite failed persistence calls, creating a false sense of completion.
- No document or task could be completed: Tasks was empty, Dossier had no forms, and upload tasks remained blocked.

Top changes: unify task sources, block or clearly label unsaved services state, and provide a specific loading message after two seconds.

### 2-C Admin and Settings

Overall: The admin console has strong density and operational styling, but role hierarchy and data consistency are weak.

- Employee, HR, and admin navigation are all visible simultaneously to the superuser.
- Admin overview reports 95 HR users and 522 active employees; Companies reports zero HR users, employees, and cases across 56 tenants.
- Company detail opens in a drawer, but user management, integrations, billing, and destructive controls were not reachable from the tested Companies flow.
- No destructive confirmation could be validated because no destructive action was exposed in the accessible flow.

Top changes: separate role contexts, unify admin metrics to one source of truth, and expose tenant users/settings through a clear detail hierarchy.
