# How requirement records reach `requirement_items`

Companion to [`README.md`](README.md). That file describes the IE→ES path; this one is the
map of **all** of them, written because there are now several and they disagree in a way
that is invisible until two of them describe the same obligation.

Measured against production on 2026-08-20 (114 rows).

## Three authoring front-ends, two landing conventions

| # | Authoring source | Lands via | `id` | `citations_json` |
|---|---|---|---|---|
| 1 | `backend/seeds/requirements/<country>.yaml` | `backend/scripts/seed_requirements.py` → `crud` | `uuid5(_SEED_NS, country\|purpose\|title)` | bare URL strings |
| 2 | Otto batches → `otto_staging.*` | `backend/imports/otto/executor.py:promote()` → `crud` | same `uuid5`, **same namespace** | source ids |
| 3 | `backend/seeds/facts/<ISO2>.yaml` (PR #1896) | `seed_corridor_facts.py` → `crud` *(not yet built)* | same `uuid5`, same namespace | source_record ids |
| 4 | `corridors/IE_ES/data/*.ndjson` + manifest | **generated SQL migration** | explicit `ES:IE-ES:<topic_key>` | inline JSON objects |

Rows 1–3 are one convention wearing three hats. `executor.py:promote()` says so out loud:

> *"Same namespace as the YAML seeder, so both writers derive the SAME id for the same
> natural key. A second namespace here would make `seed_requirements.py` and this promoter
> insert two rows for one requirement the moment their titles agreed."*

Row 4 is a different convention: it sets `id` itself and upserts with `ON CONFLICT (id)`.

The live split is clean:

```
uuid5, via crud            89 rows   8 countries
explicit colon-delimited   25 rows   1 country (SPAIN, the IE→ES batch)
```

## The actual problem: the natural key has no database backing

`crud.create_requirement_item` upserts on `(country_code, purpose, title)`. That key is
enforced **only in application code** — a `SELECT`, then an insert or update.

The sole unique constraint on the table is the primary key on `id`:

```
requirement_items_pkey   PRIMARY KEY (id)
```

There is **no unique index on `(country_code, purpose, title)`**. Two consequences:

1. **A convention-4 row and a convention-1/2/3 row for the same requirement cannot see each
   other.** `ON CONFLICT (id)` compares ids; the ids are generated by different rules, so
   they never collide. Both rows are inserted and both are served.
2. Even within the shared convention, the key holds only as long as every writer goes
   through `crud`. Nothing in the database stops a writer that does not.

## This is not hypothetical

Ireland has 14 approved, served rows. One is
**"PPSN (Personal Public Service Number) — application and emergency tax"**, a single row
covering what the #1896 fact packs split into three separately-sourced facts
(`pps_number`, `pps_proof_of_address`, `emergency_tax`), each with its own official URL,
publication date and verbatim quote.

The titles differ, so the natural key does not match, so the loader would **insert** rather
than update — and an employee would be told about PPSN and emergency tax twice, from
different sources, under different provenance badges. Caught by diffing emitted titles
against live rows before writing; the loader now holds those three for human reconciliation
rather than writing them.

A title-level diff is a workaround for a missing constraint, not a fix.

## Recommendation

**Give the natural key database backing.** As of 2026-08-20 the table has **zero**
`(country_code, purpose, title)` duplicates:

```sql
SELECT country_code, purpose, title, count(*)
FROM public.requirement_items
GROUP BY 1,2,3 HAVING count(*) > 1;   -- 0 rows
```

So a unique index is *addable today* and would convert a code convention into an enforced
invariant. It would also make convention 4 collide honestly with conventions 1–3 instead of
silently duplicating them.

Sequenced, and each step is separately reviewable:

1. **Add the unique index** (`CONCURRENTLY`, its own migration, applied out of band).
   Ships alone; nothing reads it.
2. **Point convention 4 at `crud`** — have `gen_ie_es_corridor_load.py` emit a loader call
   rather than raw `INSERT … ON CONFLICT (id)`, so all four paths share one upsert that
   already refuses to un-approve a reviewed row and refuses to overwrite an
   `expert_verified` one.
3. **Normalise `citations_json`** to source_record ids everywhere. Inline citation objects
   and bare URLs both bypass `source_records`, and `requirements_builder` silently drops any
   citation it cannot resolve there — the measured 90-with-citations / 27-resolving gap
   (`20261031000000_frno_source_records.sql`).

Step 1 is the one that pays for itself immediately; 2 and 3 can follow at any pace.

## What this document does not claim

No path here is wrong. Convention 4's generated-SQL approach has real advantages the others
lack — the sha256-verified manifest and the "generate, don't type" rule in
[`README.md`](README.md) are both good, and worth adopting the other way round. The problem
is not that four paths exist; it is that two of them cannot see each other's rows.
