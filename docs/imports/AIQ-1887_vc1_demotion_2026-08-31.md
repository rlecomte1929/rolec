# AIQ-1887 VC1 — demote a disproved fact, and stop the gap reopening

Companion to `AIQ-1887_evidence_remediation_2026-08-20.md` (D1/D2, applied) and the promoter
work in `es-ie-thirdcountry-2026-08-22-dry-run.md`. This one is about **VC1** —
*"0 facts with `status='approved'` AND `evidence_verified IS FALSE`"* — which had regressed, and
about closing the structural reason it kept regressing.

## What VC1 asks, and why the reader guard is not enough

`list_approved_requirement_facts` (`backend/db/policies.py`) serves
`status='approved' AND COALESCE(evidence_verified, TRUE) = TRUE`, so a disproved fact
(`evidence_verified IS FALSE`) is already **hidden from the dossier**. VC1 is the stronger,
data-hygiene invariant: a fact whose quote is *not on its cited page* must not keep the
`approved` badge at all. Approved is a human sign-off; a disproved fact wearing it is a latent
trust bug the day any reader forgets the `COALESCE`.

The FALSE cohort **rose from 104 to 107 during a single working session**, while TRUE fell

did not demote — every disproof it wrote reopened VC1. That is gap #2 from the 2026-08-20 doc
happening in real time:

> *"[the backfill] does not do D1; it only writes `evidence_verified`."*

Per-destination FALSE cohort at 2026-08-31: CA 38 · IE 37–40 · US 9 · DK 8 · FR 6 · NZ 3 · PT 3.
(The range on IE is the drift above; the set is whatever the query below returns at apply time.)

## The durable fix (code — this PR)

`backend/scripts/backfill_fact_evidence.py` now demotes on `--apply`: when a fact selected from
the **approved** cohort gets a **definitive FALSE** verdict, the same transaction sets its status
to `pending`.

- Only `check.verified is False` demotes. A **NULL** verdict — `NO_SOURCE` (page unreachable) or
  `TRANSLATED` — stays approved and served, exactly as the reader guard intends. Demoting on NULL
  would strip a live fact off the dossier because *our* fetcher failed; the ticket's constraints
  forbid that ("a dead source URL is signal, not a failure").
- The status write is guarded `AND status='approved'`, so it is idempotent — a strict no-op on a
  fact that is already pending or was demoted on an earlier pass.

Pinned by `backend/tests/test_backfill_demotes_disproved.py`, including the safety property that a
NULL/NO_SOURCE fact is **not** demoted.

**Operational note:** the fix only takes effect for the backfill that carries it. Whatever job was
writing FALSE verdicts to prod during this session is an **older build** — it must be redeployed
(or stopped) before the sweep below, or it will reopen VC1 again.

## The one-time cleanup (data — operator applies; not applied here)

The code fix stops *new* regressions but does not re-adjudicate the existing FALSE-and-approved
residue (a served-cohort `--only-unchecked` run skips them — they are FALSE, not NULL). Clear it
with a pure status move — no fetch, no verdict change:

```sql
-- Capture the exact rollback set FIRST, in the same session, because the cohort drifts:
\copy (SELECT id FROM requirement_facts WHERE status='approved' AND evidence_verified IS FALSE) \
  TO 'AIQ-1887_vc1_rollback_ids.csv' CSV

BEGIN;
UPDATE requirement_facts SET status='pending'
 WHERE status='approved' AND evidence_verified IS FALSE;   -- ~107 rows on 2026-08-31, drifting
-- verify VC1 == 0 before COMMIT:
SELECT count(*) FROM requirement_facts WHERE status='approved' AND evidence_verified IS FALSE;
COMMIT;
```

Rollback: `UPDATE requirement_facts SET status='approved' WHERE id IN (<the captured ids>);`

**Why no frozen id list is committed alongside this doc** (unlike 2026-08-20): the cohort is
actively drifting (104→107 within the session), so any list captured now is stale before it is
applied. The `\copy` above captures the true set at the instant of the change — the only rollback
that matches what was actually moved.

`evidence_verified` is left untouched (no verdict is invented or erased); the #1851 reader guard is
untouched; nothing is deleted. After the sweep, the patched backfill keeps VC1 at 0 on its own.
